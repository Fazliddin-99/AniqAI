# Accountant Copilot — план (конкурс PAIA, Узбекистан)

## Продукт одной фразой

Автономный конвейер, который делает рутинную работу бухгалтера в 1С:Бухгалтерия для
Узбекистана — приём документов, классификация, проводки, сверка — и эскалирует человеку
только исключения. Бухгалтер становится ревьюером, а не оператором ввода.

## Рамки MVP (для конкурса)

Только модули 1+2, одна вертикаль — торговые МСБ (максимум документов на сотрудника):

```
Didox/Faktura (ЭСФ, API) ─┐
Telegram-бот (фото/PDF)  ─┼─► Извлечение + дедупликация ─► Классификация (счёт, субконто,
Банковские выписки       ─┘                                  склад, НДС) + confidence
                                                                  │
                              высокий ──► автопроводка в 1С
                              средний ──► очередь ревью (подтверждение в 1 клик)
                              низкий  ──► эскалация с объяснением решения ИИ
```

Метрика для сцены: «N% входящих документов проведены без участия человека,
X часов бухгалтера в неделю сэкономлено». Wow-момент: голосовой Q&A на узбекском
по данным 1С (только результаты запросов, никаких сгенерированных чисел).

**Сознательно не делаем в v1:** зарплата, МСФО (апселл фазы 3), полностью автономная
сдача отчётности (кнопку «отправить» всегда жмёт человек).

## Архитектура

```
Каналы: Telegram-бот (intake) · Веб-приложение (очередь ревью, дашборд метрик)
   │
Backend-оркестратор (Claude API, tool use; мультитенантный с 1-го дня)
   │
   ├─► MCP/API-слой ──► 1С:Бухгалтерия УЗ — расширение конфигурации с HTTP-сервисами
   ├─► Didox / Faktura.uz API (входящие/исходящие ЭСФ)
   ├─► E-IMZO агент на машине бухгалтера (подпись PKCS#7)
   └─► Postgres (очередь ревью, история решений, метрики, обучающие примеры)
```

### Интеграция с 1С

- **Расширение конфигурации** с собственными HTTP-сервисами (не COM, не голый OData):
  переживает обновления типовой конфигурации, контролируемая поверхность API.
- Endpoints v1: выгрузка исторических проводок + учётной политики (обучение классификатора),
  справочники (контрагенты, номенклатура, счета, склады), создание документов
  **черновиками (непроведёнными)**, статусы, ОСВ/остатки для Q&A.
- Отдельный пользователь 1С с ограниченными правами; полный аудит-лог действий ИИ.

### Классификатор (сердце продукта)

1. **Слой 1 — детерминированные правила**: точное совпадение (тот же поставщик + тот же
   ИКПУ/номенклатура, что уже проводились) → автопроводка без LLM. Дёшево и даёт
   базовые ~50–70% на зрелых базах.
2. **Слой 2 — LLM + retrieval**: похожие исторические проводки этой компании (поиск по
   поставщику/ИКПУ/названию) подаются как few-shot контекст; Claude возвращает проводку
   + confidence + объяснение («классифицировано как материалы, т.к. похожие позиции этого
   поставщика ранее проводились на 1010»).
3. **Обучение на исправлениях**: каждая правка бухгалтера сохраняется как обучающий пример
   и попадает в retrieval → точность видимо растёт по месяцам (метрика для жюри и retention).
4. Confidence калибруется по фактическим исправлениям, пороги настраиваются per-tenant.

### E-IMZO (подпись)

- Агент в трее на машине бухгалтера, говорит с локальным WebSocket E-IMZO (CAPIWS):
  утром бухгалтер один раз вводит пароль ключа (штатный диалог `pfx.load_key`) → агент
  держит key id сессии → весь день `pkcs7.create_pkcs7` без GUI → подпись в Didox.
- UX по умолчанию — **батч-подпись**: «Подписать все 47» после ревью утренней очереди.
  Полностью фоновая подпись — opt-in. Ключи и пароли никогда не покидают машину клиента,
  ничего не централизуем.
- Обработать истечение сессии (уведомление «введите пароль заново», не тихий фейл ночного батча).
- Референс интеграции: репозиторий qo0p/e-imzo-doc (GitHub).

## Метрики (инструментировать с 1-го дня — это KPI траншей)

- % автопроведённых документов; точность классификации (после исправлений)
- часов сэкономлено в неделю на компанию; документов в месяц
- предотвращённые ошибки/штрафы (шт. и сумма в сумах)

## Пилоты

Первые клиенты — **бухгалтерские аутсорсинговые фирмы** (одна фирма в Ташкенте = 30–80
компаний на 1С): максимальная боль от рутины, разнообразные данные для обучения,
одна продажа = десятки компаний. Цель — 2 фирмы-пилота до дедлайна подачи заявки.

## План работ, привязанный к календарю

**Спринт 0 — до 1 августа (заявка).** Команда есть — приоритет смещается на прототип и
заявку. Прототип-скелет: фича 1 (Telegram-приём фото/сканов → черновик в 1С, на моке)
+ классификатор на выборке ЭСФ + 1–2-минутное демо-видео. Начать разговор с 1–2
аутсорсинговыми фирмами. Уточнить объём Didox-интеграции в БП 3.0.

**Спринт 1 — 2–20 августа (к питчу).** Вертикальный срез end-to-end на тестовой базе 1С:
расширение 1С (read-only + создание черновиков) → выгрузка исторических проводок →
классификатор (правила + LLM + confidence) → веб-очередь ревью → черновик документа в 1С.
Инструментировать метрики с первого дня.

**Спринт 2 — 21 авг – 5 сен (питч).** Живое демо конвейера + цифры с тестовой базы.
Питч-нарратив: «бухгалтер-ревьюер, не оператор»; договорённости о пилотах как traction.

**Спринт 3 — 6 сен – 30 ноя (акселерация).** Пилоты в 2 аутсорсинговых фирмах:
мультитенантность, Telegram-intake, дедупликация, E-IMZO агент (батч-подпись),
дашборд метрик, обучение на исправлениях. Цель к полуфиналу — реальные цифры:
% автопроводок, часы/неделю, рост точности по месяцам.

**Спринт 4 — декабрь (полуфинал и Demo Day).** Узбекский голосовой Q&A как wow-момент,
отполированное демо, метрики пилотов на слайде.

## Решённые вопросы

- **Команда** — укомплектована: основатель + 2 ИИ-инженера = 3 (требование PAIA 3–8 ✔).
- **Didox** — интеграция уже в типовой БП 3.0: входящие ЭСФ грузятся штатно. Свой
  партнёрский API Didox для базового потока НЕ нужен — источник ЭСФ = сама база 1С
  через наше расширение. (Партнёрский API может понадобиться позже для realtime-push;
  для MVP — не блокер.) Следствие: **фича 1 (Telegram) закрывает то, чего Didox не
  делает** — фото/сканы/чеки/банковские выписки/инвойсы. Это и есть дифференциация.

## Риски / проверить в первую очередь

1. **Что именно покрывает Didox-интеграция БП 3.0** — уточнить: только загрузка входящих
   ЭСФ, или и сопоставление с документами. От этого зависит, где наша ценность на ЭСФ-потоке.
2. **Разнообразие баз 1С у пилотов** (версии конфигурации УЗ, доработки) — расширение
   тестировать минимум на двух реальных релизах конфигурации.
4. Персональные данные и ключи: ничего чувствительного на нашей стороне; on-premise
   компоненты (агент, коннектор 1С) — у клиента.
5. Налоговые ответы ассистента — только через RAG по НК РУз/НСБУ с цитатами, никаких
   ставок «из головы» модели.
