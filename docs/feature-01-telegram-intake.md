# Фича 1: Telegram-intake → классификация операции → черновик в 1С

## Что делает

Пользователь (директор/бухгалтер) кидает в Telegram-бот фото, файлы (PDF/Excel) и текст.
Бот понимает, какая это хозяйственная операция, собирает структурированный JSON и отправляет
его в API 1С для создания **непроведённого черновика** документа. Недостающее уточняет
вопросами. То, чего не умеет, — честно называет.

## Ключевое архитектурное решение: бот — это агент, а не пайплайн

Не «распознать фото → форма → отправить», а **диалоговый агент на Claude (tool use)**,
живущий в контексте чата. Все требования фичи тогда получаются естественно:

| Требование | Как решается агентной моделью |
|---|---|
| Фото сейчас, инструкция следующим сообщением | Это просто следующая реплика в той же беседе — контекст общий |
| Текстовые инструкции («проведи как возврат») | Обычное сообщение пользователя, агент учитывает |
| Уточняющие вопросы | Агент сам решает: хватает данных → tool call, не хватает → вопрос текстом |
| Честность о возможностях | Закрытый список tools + системный промпт: «вне списка — скажи, что не умеешь» |
| Классификация операции | Поле `operation_type` в схеме tool'а `create_operation` (strict JSON schema) |

## Схема

```
Telegram ──(aiogram, long polling)──► Bot-слой (apps/bot)
                                        │  буферизация сообщений: media_group +
                                        │  дебаунс 2–3 с → одна «реплика» пользователя
                                        ▼
                              Agent core (apps/backend)
                              Claude tool runner, per-chat история
                              (фото → image block, PDF → document block)
                                        │
              ┌─────────────────────────┼──────────────────────────┐
              ▼                         ▼                          ▼
   find_counterparty(tin|name)   find_item(query)        create_operation(json)
              └────────────── 1С Gateway (HTTP-клиент) ────────────┘
                                        │
                              1С HTTP-сервис /hs/copilot/v1
                              (расширение конфигурации; в dev — мок на FastAPI)
```

### Bot-слой (apps/bot, Python + aiogram 3)

- Принимает `text`, `photo`, `document` (PDF, XLSX), `caption`.
- **Буферизация**: сообщения одного чата копятся 2–3 секунды (альбомы — по
  `media_group_id`), затем передаются агенту одной репликой. Пользователи шлют
  «фото → фото → подпись» очередью — это должно стать одним ходом.
- Если агент уже обрабатывает ход, новые сообщения встают в очередь чата и уходят
  следующим ходом (не теряются).
- Скачивает файлы во временное хранилище, отдаёт агенту как base64.
- **Авторизация**: whitelist `telegram_user_id → компания (база 1С)`. Незнакомый
  пользователь получает отказ. Это же — точка мультитенантности.
- Голосовые в v1 не поддерживаем → бот честно говорит об этом (кандидат на v2).

### Agent core (apps/backend)

Claude Opus 4.8, диалоговый цикл tool use, per-chat история сообщений
(обрезка/компакция при разрастании).

**LLM за интерфейсом-провайдером** (`app/agent/providers`): ядро работает с
провайдер-нейтральными блоками (`Message`, `TextBlock`, `ImageBlock`, `ToolUseBlock`…),
конкретный провайдер переводит их в свой формат. Переключение — `LLM_PROVIDER`:
- `anthropic` (по умолчанию) — Claude, максимальная точность для заявки и пилотов;
- `openai` — локальная модель через OpenAI-совместимый сервер (vLLM/Ollama).
  Рекомендуемая: **Qwen2.5-VL** 32B/72B (зрение + tool calling + русский). Env:
  `LOCAL_LLM_URL`, `LOCAL_LLM_MODEL`. Ограничение: PDF пока требует рендера страниц
  в изображения (не реализовано) — картинки работают.

Стратегия: демо/пилоты на Claude; локальная модель — позже, как опция приватности
(данные не покидают инфраструктуру клиента) и для гибридной маршрутизации
(простое — локально, сложное — Claude).

**Tools (закрытый список = граница возможностей v1):**

| Tool | Что делает |
|---|---|
| `find_counterparty(tin?, name?)` | Поиск контрагента в 1С — проверить, что поставщик/покупатель существует, уточнить ИНН |
| `find_item(query)` | Поиск номенклатуры в 1С — маппинг позиций документа на справочник |
| `create_operation(operation)` | Отправить структурированную операцию в 1С (strict schema, см. ниже) |

**Типы операций v1** (enum в схеме — классификация принудительно ограничена):

- `goods_receipt` — поступление товаров/услуг (входящий СФ, накладная)
- `sales_invoice` — реализация (исходящий счёт)
- `expense_receipt` — чек/квитанция (подотчёт, мелкие расходы)
- `payment_order` — платёжное поручение

Всё остальное (зарплата, отчётность, кадры, «посчитай налог») — **вне tools**:
системный промпт требует честно ответить «этого я пока не умею, умею: …» и записать
запрос в лог `unsupported_requests` (это бэклог продукта — видно, что просят чаще всего).

**Правила поведения агента (системный промпт):**

1. Не выдумывать реквизиты. Нет даты/суммы/контрагента на фото и в тексте → спросить.
   Один конкретный вопрос за ход, с вариантами, если они есть.
2. Числа — только из документа или слов пользователя, никогда «по памяти».
3. Перед `create_operation` — показать пользователю карточку-резюме (см. UX).
4. Инструкция пользователя главнее классификации («это возврат» → переклассифицировать
   или честно сказать, что возвраты пока не поддерживаются).

### UX подтверждения (человек в контуре)

Перед отправкой в 1С бот показывает карточку:

> 📄 **Поступление товаров** от OOO "MEGA TRADE GROUP" (ИНН 304444555)
> СФ №1187 от 16.07.2026 · 2 позиции · 43 500 000 сум + НДС 5 220 000
> ✅ Отправить в 1С  ✏️ Исправить  ❌ Отмена

- ✅ → `create_operation` → ответ с номером черновика в 1С.
- ✏️ → пользователь пишет исправление текстом, агент обновляет карточку.
- В v1 подтверждение обязательно всегда (флаг автоотправки при высоком confidence —
  осознанный opt-in позже; это соответствует принципу «бухгалтер — ревьюер»).

### Контракт операции (payload `create_operation` → 1С)

```json
{
  "operation_type": "goods_receipt",
  "confidence": 0.93,
  "external_id": "tg-<chat_id>-<message_id>",
  "source": {"channel": "telegram", "chat_id": 123, "file_ids": ["..."]},
  "counterparty": {"name": "OOO MEGA TRADE GROUP", "tin": "304444555", "ref_1c": null},
  "document": {"number": "1187", "date": "2026-07-16"},
  "items": [
    {"name": "Смартфон Infinix Hot 40i", "ikpu": "08517140001000000",
     "qty": 30, "price": 1450000, "sum": 43500000, "vat_rate": 12, "vat_sum": 5220000,
     "item_ref_1c": null}
  ],
  "totals": {"sum": 43500000, "vat_sum": 5220000},
  "user_comment": "принял завхоз, склад №2",
  "explanation": "классифицировано как поступление: входящий СФ, покупатель — наша компания"
}
```

`external_id` — ключ идемпотентности (повторная отправка того же документа не создаёт
дубль). `ref_1c` заполняются, если tools нашли объект в справочниках.

### API 1С (HTTP-сервис расширения конфигурации, base `/hs/copilot/v1`)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/counterparties?tin=&name=` | Поиск контрагентов (код, ИНН, наименование) |
| GET | `/items?query=` | Поиск номенклатуры |
| POST | `/operations` | Создать **непроведённый** черновик документа из контракта выше. Заголовок `Idempotency-Key: <external_id>`. Ответ: `{"draft_id", "doc_type_1c", "doc_number", "status": "draft"}` |
| GET | `/operations/{draft_id}` | Статус черновика (draft / posted / rejected) |

- Auth: Basic, отдельный пользователь 1С с правами только на нужные документы.
- Маппинг `operation_type → документ 1С`: goods_receipt → «Поступление товаров и услуг»,
  sales_invoice → «Реализация товаров и услуг», expense_receipt → «Авансовый отчёт»,
  payment_order → «Платёжное поручение (исходящее)».
- **В dev 1С заменяется моком** (`apps/onec-mock`, FastAPI): та же схема, черновики
  пишутся в JSON-файлы. Это позволяет собрать и показать фичу целиком до готовности
  расширения (само расширение — через `/setup-1c-framework`).

### Хранилище (apps/backend)

SQLite в v1 (Postgres на пилоте): таблицы `chats` (история агента, компания),
`operations` (контракт + статус + confidence), `unsupported_requests`, `metrics_events`.

## Метрики с первого дня

- документов принято / классифицировано / отправлено в 1С;
- % операций без единого уточняющего вопроса (прокси качества извлечения);
- % карточек, подтверждённых без исправлений (точность классификации);
- топ неподдержанных запросов.

## План работ

| # | Шаг | Оценка | Результат |
|---|---|---|---|
| 1 | Контракт операции в `packages/shared` + мок 1С API | 0.5 дн | Есть куда отправлять |
| 2 | Bot-слой: aiogram, приём text/photo/document, буферизация, whitelist | 1 дн | Сообщения доходят одной репликой |
| 3 | Agent core: tool runner, системный промпт, vision, 3 tools | 1–2 дн | Фото ЭСФ → карточка операции |
| 4 | Карточка подтверждения (inline-кнопки), правки текстом, идемпотентность | 1 дн | Полный цикл до мока 1С |
| 5 | Лог unsupported + метрики + прогон на 10–20 реальных фото | 0.5 дн | Демо-цифры |
| 6 | Реальный HTTP-сервис 1С (расширение, `/setup-1c-framework`) | 2–3 дн, параллельно | Мок заменяется живой базой |

Итого ~4–5 дней до работающей фичи на моке, +2–3 дня до живой 1С. Укладывается в
спринт 1 (2–20 августа) с запасом; шаги 1–3 можно успеть до подачи заявки.

## Крайние случаи (учтены в дизайне)

- Альбом из нескольких фото одного документа → одна реплика (media_group).
- Инструкция после фото / до фото → общий контекст чата.
- Повторная отправка того же документа → идемпотентность по `external_id` + позже
  дедуп по (ИНН поставщика, номер, дата).
- Нечитаемое фото → агент честно говорит и просит переснять.
- Несколько документов в одном сообщении → агент обрабатывает по одному,
  проговаривая порядок.
- Сообщение во время обработки → очередь чата, обработается следующим ходом.
