# ТЗ: HTTP-сервис «Copilot» для «1С:Бухгалтерия для Узбекистана» (ред. 3.0)

Версия 1.1 · 2026-07-20 · Статус: к реализации

Этот документ самодостаточен — его можно передать разработчику 1С без остального
репозитория. Вопросы по контракту — к команде бэкенда.

> **Что изменилось в 1.1.** Добавлены приоритетные операции: **чек подотчётного лица**
> (доработан) и **ГТД по импорту** (новая, §5.7). Появился пятый эндпоинт — поиск
> сотрудников (§4.5). Ответ на POST теперь может содержать **несколько** созданных
> документов (§5.6). Приоритет реализации: сначала `expense_receipt` и
> `customs_declaration`, затем остальные типы.

---

## 1. Что нужно сделать (кратко)

**Расширение конфигурации** (не изменение типовой!) для «1С:Бухгалтерия для
Узбекистана, ред. 3.0», которое публикует **HTTP-сервис** с пятью операциями:

| # | Метод | URL | Назначение |
|---|-------|-----|-----------|
| 1 | GET | `/hs/copilot/v1/counterparties` | Поиск контрагентов по ИНН или названию |
| 2 | GET | `/hs/copilot/v1/items` | Поиск номенклатуры по названию или ИКПУ |
| 3 | GET | `/hs/copilot/v1/employees` | Поиск физлиц-сотрудников (подотчётные лица) |
| 4 | POST | `/hs/copilot/v1/operations` | Создать **непроведённый** документ из JSON-операции (с идемпотентностью) |
| 5 | GET | `/hs/copilot/v1/operations/{draft_id}` | Статус созданного документа |

Вызывать сервис будет внешний бэкенд (ИИ-ассистент): он присылает уже
структурированную операцию, задача 1С-стороны — найти/создать объекты и записать
документ **черновиком**. Проводит документы всегда живой бухгалтер в 1С.

Ключевые принципы:

1. **Только расширение.** Типовая конфигурация не дорабатывается — расширение должно
   переживать обновления релизов.
2. **Создание никогда не проводит документы.** POST `/operations` — только `Записать()`
   без проведения. Проведение существует, но ТОЛЬКО отдельным вызовом §6.1 после
   явного подтверждения пользователя кнопкой в боте (решение владельца проекта,
   dev-чат 31.07.2026; ранее действовал полный запрет).
3. **Идемпотентность обязательна.** Повторный POST с тем же ключом не создаёт дубль.
4. **Отдельный пользователь 1С** с минимальными правами (см. §7).

---

## 2. Общие требования к сервису

- Имя HTTP-сервиса: `copilot`, корневой URL: `/hs/copilot/v1/...`
  (публикация стандартная: Администрирование → Публикация на веб-сервере, или через
  существующую публикацию базы).
- Формат: JSON, UTF-8, `Content-Type: application/json`.
- Аутентификация: **Basic** (стандартная аутентификация 1С). Логин/пароль — учётная
  запись из §7. HTTPS обязателен в продуктиве.
- Все ответы об ошибках — единый формат (§6). Внутренние исключения не должны
  «протекать» наружу текстом платформы — перехватывать и оборачивать.
- Даты в JSON: строки `ГГГГ-ММ-ДД` (например `2026-07-16`).
- Числа (суммы, количества): JSON number, суммы в сумах (UZS), без строк.
- Неизвестные поля во входном JSON — игнорировать (вперёд-совместимость).

## 3. Эндпоинт 1: поиск контрагентов

```
GET /hs/copilot/v1/counterparties?tin=304444555
GET /hs/copilot/v1/counterparties?name=MEGA
```

Параметры (хотя бы один): `tin` — ИНН/СТИР (точное совпадение, 9 цифр) или ПИНФЛ (14);
`name` — подстрока наименования, регистронезависимо.

Поиск по справочнику «Контрагенты», исключая помеченные на удаление.
Ограничить выдачу 20 элементами.

**Ответ 200** — массив (возможно пустой):

```json
[
  {
    "ref_1c": "a3f2c8d1-...-guid",
    "name": "OOO \"MEGA TRADE GROUP\"",
    "tin": "304444555"
  }
]
```

`ref_1c` — строка УникальныйИдентификатор ссылки (GUID). `tin` может быть `null`,
если у контрагента не заполнен ИНН.

## 4. Эндпоинт 2: поиск номенклатуры

```
GET /hs/copilot/v1/items?query=цемент
GET /hs/copilot/v1/items?query=06810001001000000
```

`query` — подстрока наименования (регистронезависимо) **или** код ИКПУ (если строка
состоит из 17 цифр — искать по реквизиту ИКПУ). Справочник «Номенклатура», без
помеченных на удаление, лимит 20.

**Ответ 200:**

```json
[
  {
    "ref_1c": "b7e1a9c2-...-guid",
    "name": "Цемент М400, мешок 50 кг",
    "ikpu": "06810001001000000",
    "unit": "шт"
  }
]
```

`ikpu` — код из каталога tasnif.soliq.uz, как он хранится в карточке номенклатуры
БП УЗ; `null`, если не заполнен. `unit` — представление базовой единицы измерения.

## 4.5. Эндпоинт 3: поиск сотрудников (подотчётных лиц)

```
GET /hs/copilot/v1/employees?query=Каримов
```

Нужен для `expense_receipt`: агент уточняет у пользователя ФИО подотчётного лица и
резолвит его в ссылку 1С до создания документа.

`query` — подстрока ФИО, регистронезависимо; **многословный запрос («Иванов Иван»)
обязан находить полное ФИО, содержащее его как подстроку**. Кодировка параметра —
URL-encoded UTF-8. Искать по справочнику, который в БП УЗ
подставляется в реквизит «Подотчётное лицо» документа «Авансовый отчёт»
(**Физические лица**; если в конкретной конфигурации там Сотрудники — искать по нему
и вернуть ссылку того типа, который принимает реквизит). Без помеченных на удаление.

Параметр `limit` (согласовано в dev-чате 31.07.2026): по умолчанию 20, потолок 100.

**Ответ 200:**

```json
[
  {
    "ref_1c": "d4a8b1e5-...-guid",
    "name": "Каримов Азиз Рустамович",
    "position": "Менеджер по снабжению"
  }
]
```

`position` — должность, если доступна; иначе `null`. Поле справочное: помогает
пользователю выбрать нужного человека при совпадении фамилий.

## 4.6. Эндпоинт 4: список складов (согласовано 31.07.2026)

```
GET /hs/copilot/v1/warehouses?query=&limit=
```

Параметры и лимиты — как у `/items`. **Ответ 200:** массив `{ "ref_1c", "name" }`,
без помеченных на удаление. Нужен боту, чтобы при нескольких складах уточнить выбор
у пользователя (требование пользователя от 31.07.2026); при единственном складе бот
ничего не спрашивает и полагается на фолбэк §5.5.

## 4.7–4.9. Отчётные эндпоинты для аналитики директора (добавлено 14.08.2026, v1.2)

Назначение: бот отвечает на вопросы директора («почему продажи упали», «какие расходы
самые большие», «сколько нам должны») цифрами **только из этих отчётов** — модель
никогда не выдумывает числа. Общие правила для всех трёх:

- **Только чтение**, только агрегаты — сырые записи регистров наружу не отдаются.
  Доступ через привилегированный режим (§7), как у остальных методов.
- Учитываются только **проведённые** документы / фактические движения регистров.
- `date_from`/`date_to` — включительно, формат `ГГГГ-ММ-ДД`.
- `limit` — по умолчанию 20, потолок 100 (конвенция §4.5). Строки сортируются по
  убыванию сумм. **`total` всегда считается по полному набору данных**, даже если
  `rows` обрезаны (`"truncated": true`) — клиент вычисляет «остальные» как
  total − Σ rows.
- Ролевого ограничения в v1 нет: отчёты видит любой активный пользователь компании
  (данные и так company-scoped; поле `role` зарезервировано на будущее).
- Суммы — в сумах; валютные показатели — в регламентном (суммовом) выражении,
  если явно не сказано иное.

**Уточнения по итогам реализации в 1С (14.08.2026), проверены на реальной базе:**

- **Организация.** Отчёт считается по организации из настройки §5.5, если она задана
  однозначно; иначе — по всем организациям базы. Выбранный вариант возвращается в
  поле `organization` каждого ответа (при отсутствии настройки — строка
  «все организации»). Молчаливый выбор одной организации из нескольких запрещён:
  директор увидел бы цифры неизвестно чьей компании.
- **Коды валют** (`currency`) отдаются буквенным ISO 4217 (`UZS`, `USD`). Наименование
  элемента справочника для этого не годится: в базе валюта регламентированного учёта
  может называться «сум.» — тогда код выводится из цифрового кода валюты.
- **Сортировка строк** — не по обороту, а по «весу» строки (оборот + конечный
  остаток). На счетах расчётов за короткий период оборотов может не быть вовсе, и
  в обрезанную лимитом выдачу попадали бы случайные контрагенты вместо крупнейших
  должников — то есть ровно не те, ради кого отчёт запрашивают.

### 4.7. Обороты и остатки по счёту (универсальный отчёт)

```
GET /hs/copilot/v1/reports/account?account=4010&date_from=2026-01-01&date_to=2026-07-31&group_by=subconto1&limit=20
```

| Параметр | Обяз. | Описание |
|---|---|---|
| `account` | ✅ | Код счёта плана счетов НСБУ (`4010`, `9420`…). Префиксный: `9420` включает субсчета |
| `date_from`, `date_to` | ✅ | Период |
| `group_by` | — | `none` (по умолчанию — только итог) \| `subconto1` \| `subconto2` \| `month` |
| `limit` | — | 20 / cap 100 |

Источник — регистр бухгалтерии (эквивалент ОСВ по счёту). **Ответ 200:**

```json
{
  "account": "4010",
  "account_name": "Счета к получению от покупателей и заказчиков",
  "date_from": "2026-01-01", "date_to": "2026-07-31",
  "group_by": "subconto1",
  "total": { "opening_debit": 0, "opening_credit": 0,
             "turnover_debit": 1250000000, "turnover_credit": 1090000000,
             "closing_debit": 160000000, "closing_credit": 0 },
  "rows": [
    { "name": "OOO \"MEGA TRADE GROUP\"", "ref_1c": "guid-или-null",
      "kind": "Контрагенты",
      "opening_debit": 0, "opening_credit": 0,
      "turnover_debit": 420000000, "turnover_credit": 330000000,
      "closing_debit": 90000000, "closing_credit": 0 }
  ],
  "truncated": false
}
```

`kind` — имя вида субконто строки («Контрагенты», «Договоры», «Статьи затрат»…);
`null` для `group_by=month|none`. Добавлено по вопросу 1С 14.08.2026: у счетов разные
виды субконто, и клиенту (подписи графиков) полезно знать, что именно в строках.
**1С поле отдаёт** (реализовано и проверено 14.08.2026: 4010/subconto1 → «Контрагенты»,
4010/subconto2 → «Договоры»). Берётся из вида субконто счёта, а не из значения строки,
поэтому заполнено и у строки «&lt;без аналитики&gt;».
Для `group_by=month` в `name` — `"2026-06"`, `ref_1c: null`.
Ошибки: 400 `bad_request` (нет `account`/дат, неверный `group_by`),
404 `account_not_found`.

### 4.8. Продажи по периодам

```
GET /hs/copilot/v1/reports/sales?date_from=2026-01-01&date_to=2026-07-31&granularity=month&dimension=item&limit=10
```

| Параметр | Обяз. | Описание |
|---|---|---|
| `date_from`, `date_to` | ✅ | Период |
| `granularity` | — | `month` (по умолчанию) \| `day` |
| `dimension` | — | `none` (по умолчанию) \| `item` \| `counterparty` — разрез внутри каждого периода |
| `limit` | — | размер breakdown на период, 10 / cap 100 |

`revenue` — выручка **без НДС** (кредитовый оборот 9010 по проведённым реализациям),
`cost` — себестоимость (дебетовый оборот 9110), `qty` — суммарное количество,
`doc_count` — число документов реализации. **Ответ 200:**

```json
{
  "date_from": "2026-01-01", "date_to": "2026-07-31",
  "granularity": "month", "dimension": "item",
  "periods": [
    { "period": "2026-06", "revenue": 480000000, "cost": 340000000,
      "qty": 1250, "doc_count": 42,
      "breakdown": [
        { "name": "Смартфон Samsung Galaxy A15", "ref_1c": "guid",
          "revenue": 210000000, "cost": 160000000, "qty": 700 }
      ],
      "truncated": false }
  ]
}
```

При `dimension=none` — `breakdown: []`. **Периоды без продаж включаются с нулями** —
агент должен видеть провалы, а не пропуски.

**Ограничения источника (измерены на реальной базе 14.08.2026 — учитывать при
формулировках бота):**

- `dimension=item` группирует по **номенклатурной группе**, а не по конкретной
  номенклатуре: субконто счетов 9010/9110 — номенклатурная группа, номенклатуры в
  этих проводках нет. Отраслевого регистра продаж в БП УЗ не существует, а
  `РегистрНакопления.СведенияОРеализация` в конфигурации не заполняется (проверено:
  за месяцы с оборотом 9010 в 18 млрд регистр пуст). Бот обязан называть такие
  строки группами товаров, а не товарами.
- `cost` **внутри `breakdown` всегда 0**: проводка себестоимости (Дт 9110) не
  содержит ни контрагента, ни аналитики выручки, поэтому разложить себестоимость
  по тем же разрезам нечем. Итог периода (`periods[].cost`) при этом верный.
  Ноль здесь означает «нет данных в этом разрезе» — распределять итог пропорцией
  запрещено: получилась бы правдоподобная выдуманная цифра.
- `qty` заполняется только там, где по счёту ведётся количественный учёт; на
  типовых 9010/9110 количества нет, и поле возвращает 0.
- **Потолок 400 интервалов** на ответ: `granularity=day` за многолетний период
  отклоняется с `bad_request` — периоды без продаж включаются нулями, и без потолка
  ответ раздувается до тысяч строк. Сузьте период или возьмите `granularity=month`.

Сверка проведена: `revenue` по месяцам совпадает с кредитовым оборотом 9010 из §4.7
до копейки, суммы `breakdown` — с итогом периода.

### 4.9. Денежные средства на дату

```
GET /hs/copilot/v1/reports/cash?date=2026-08-14
```

`date` — остатки на конец дня; не указана → сегодня. Кассы (5010) и банковские
счета (5110, валютные 5210). **Ответ 200:**

```json
{
  "date": "2026-08-14",
  "total_uzs": 154000000,
  "accounts": [
    { "kind": "bank", "name": "Осн. р/с АКБ Kapitalbank", "account": "5110",
      "currency": "UZS", "balance": 120000000, "balance_uzs": 120000000 },
    { "kind": "cash", "name": "Основная касса", "account": "5010",
      "currency": "UZS", "balance": 34000000, "balance_uzs": 34000000 }
  ]
}
```

`kind`: `bank` | `cash`. Для валютных счетов `balance` — в валюте,
`balance_uzs` — по курсу на `date`.

## 5. Эндпоинт 4: создание операции (главный)

```
POST /hs/copilot/v1/operations
Idempotency-Key: tg-987654321-a1b2c3d4
Content-Type: application/json
```

### 5.1. Входной JSON (контракт)

```json
{
  "operation_type": "goods_receipt",
  "confidence": 0.93,
  "external_id": "tg-987654321-a1b2c3d4",
  "source_channel": "telegram",
  "counterparty": {
    "name": "OOO \"MEGA TRADE GROUP\"",
    "tin": "304444555",
    "ref_1c": "a3f2c8d1-...-guid"
  },
  "doc_number": "1187",
  "doc_date": "2026-07-16",
  "items": [
    {
      "name": "Смартфон Infinix Hot 40i",
      "ikpu": "08517140001000000",
      "qty": 30,
      "price": 1450000,
      "sum": 43500000,
      "vat_rate": 12,
      "vat_sum": 5220000,
      "item_ref_1c": "b7e1a9c2-...-guid"
    }
  ],
  "totals": { "sum": 43500000, "vat_sum": 5220000 },
  "user_comment": "принял завхоз, склад №2",
  "explanation": "классифицировано как поступление: входящий СФ"
}
```

Поля:

| Поле | Обяз. | Описание |
|------|-------|----------|
| `operation_type` | ✅ | Одно из: `goods_receipt`, `sales_invoice`, `expense_receipt`, `payment_order`, `customs_declaration` (§5.3) |
| `confidence` | ✅ | 0..1, уверенность ИИ. Записать в комментарий документа, в логику не вмешивать |
| `external_id` | ✅* | Ключ идемпотентности (*либо заголовок `Idempotency-Key` — приоритет у заголовка; нет ни того ни другого → 400) |
| `counterparty.ref_1c` | — | GUID контрагента, если бэкенд его нашёл через эндпоинт 1. Если `null` — искать по `tin`, потом по `name`; не нашли → **создать** нового контрагента (Наименование=`name`, ИНН=`tin`) с пометкой в комментарии «создан ассистентом» |
| `doc_number` | — | Номер входящего первичного документа (не номер, который присвоит 1С!). Максимум **30 символов** — длиннее реквизит «Номер вх. документа» не вмещает, сервис отвечает 422 (молча обрезать нельзя: обрезанный номер может совпасть с чужим). Согласовано 31.07.2026 |
| `doc_date` | — | Дата документа; `null` → текущая дата |
| `items[].item_ref_1c` | — | GUID номенклатуры, если найден. `null` → искать по `ikpu`, потом по `name`; не нашли → **создать** номенклатуру (Наименование=`name`, ИКПУ=`ikpu`) |
| `items[].sum` | ✅ | Сумма строки **без НДС**, UZS |
| `items[].vat_rate` | — | Ставка НДС в процентах (12 или 0). Маппить на перечисление ставок НДС конфигурации |
| `totals` | ✅ | Контрольные итоги. Если расходятся с суммой строк более чем на 1 сум — ответ 422 (§6) |
| `warehouse_ref` | — | GUID склада из §4.6. Заполнен → использовать его; пуст → фолбэк §5.5 (константа/единственный склад). Согласовано 31.07.2026 |
| `user_comment`, `explanation` | — | Записать в поле Комментарий документа (см. шаблон §5.4) |
| `items[].kind` | — | `goods` (по умолчанию) или `service`. Определяет табличную часть: Товары или Услуги/Прочее |
| `currency` | — | Код валюты, по умолчанию `UZS`. Для импорта — валюта договора (`USD`, `EUR`, …) |
| `exchange_rate` | — | Курс к суму на `doc_date`. `null` → 1С берёт курс из регистра сама |
| `expense_details` | ✅ для `expense_receipt` | Блок подотчёта, §5.3.1 |
| `customs_details` | ✅ для `customs_declaration` | Блок ГТД, §5.7 |

Блоки `expense_details` и `customs_details` для остальных типов операций отсутствуют
или равны `null` — контракт плоский и совместим вперёд: реализация `goods_receipt`
не меняется от их появления.

### 5.2. Идемпотентность (обязательно)

- Завести **регистр сведений** в расширении, например `коп_СозданныеОперации`:
  Измерение: `КлючИдемпотентности` (Строка 100).
  Ресурсы: `Документ` (ссылка), `ТипДокумента` (Строка), `Ответ` (Строка — сериализованный JSON ответа).
- Алгоритм POST:
  1. Ключ = заголовок `Idempotency-Key`, иначе `external_id` из тела; нет → 400.
  2. Если запись с таким ключом есть → вернуть **сохранённый ответ** с
     `"idempotent_hit": true`, HTTP 200. Ничего не создавать.
  3. Иначе создать документ, записать регистр, вернуть ответ с `"idempotent_hit": false`.
- Создание документа и запись регистра — в **одной транзакции**.

### 5.3. Маппинг операций на документы БП 3.0 (Узбекистан)

| `operation_type` | Документ 1С | Заполнение |
|---|---|---|
| `goods_receipt` | Поступление товаров и услуг | Контрагент, договор (основной/создать «Основной договор»), дата=`doc_date`, «Номер вх. документа»=`doc_number`, табличная часть Товары (или Услуги — если у номенклатуры вид «Услуга»): номенклатура, кол-во, цена, сумма, ставка/сумма НДС. Склад — основной склад организации |
| `sales_invoice` | Реализация товаров и услуг | Аналогично; покупатель = `counterparty` |
| `expense_receipt` | Авансовый отчёт | Подотчётное лицо — **из `expense_details`**, не константа (§5.3.1) |
| `payment_order` | Платёжное поручение (исходящее) | Получатель = `counterparty`, сумма = `totals.sum + totals.vat_sum`, назначение платежа = `user_comment` либо `explanation`; счёт организации — основной |
| `customs_declaration` | **Пара:** Поступление товаров и услуг + ГТД по импорту | Создаются оба документа за один вызов, §5.7 |

Общее для всех: **при создании документ только записывается (`Записать()`), не
проводится** (проведение — отдельный вызов §6.1 по подтверждению пользователя);
организация — из настройки расширения (§5.5); валюта — `currency` (по умолчанию UZS).

Если тип пришёл не из списка — 422 с кодом `unsupported_operation_type` (на случай
рассинхронизации версий, бэкенд валидирует раньше).

### 5.3.1. Чек подотчётного лица (`expense_receipt`) — приоритет 1

Документ **«Авансовый отчёт»** (раздел Банк и касса).

```json
"expense_details": {
  "accountable_person": {
    "name": "Каримов Азиз Рустамович",
    "ref_1c": "d4a8b1e5-...-guid"
  }
}
```

- **Подотчётное лицо обязательно и приходит от бэкенда.** Агент уточняет его у
  пользователя и резолвит через §4.5. Если `ref_1c` пуст — искать по `name`;
  не нашли → **422 `employee_not_found`**. Физлиц создавать **нельзя** (в отличие от
  контрагентов и номенклатуры): ошибочно созданный сотрудник ломает кадровый учёт
  и расчёты по подотчёту.
- Шапка: Дата = `doc_date`, Организация и Склад — из настроек §5.5,
  Способ учёта НДС — по умолчанию конфигурации.
- **Валюта документа заполняется явно** (из `currency`, по умолчанию — валюта
  регламентированного учёта), вместе с курсом и кратностью на `doc_date`; при
  отсутствии записи в регистре курсов подставляется 1/1. Причина: документ создаётся
  без формы, а `ОбработкаЗаполнения` валюту не ставит — пустая валюта не равна валюте
  регл. учёта, и проведение уходит в валютную ветку и отказывает («Не задана кратность
  валюты … на дату …»). Уточнено 14.08.2026 по замеру на реальном документе.
- **Раскладка позиций по закладкам** по полю `items[].kind`:
  `goods` → закладка **«Товары»**, `service` → закладка **«Прочее»**.
  Одна операция может содержать оба вида — тогда заполняются обе закладки.
- Закладку **«Авансы»** не заполнять: сопоставление с выданным авансом делает
  бухгалтер вручную (автоподбор без контроля остатка даёт неверные проводки).
- Счёт авансов и Назначение в подвале — по умолчанию конфигурации.
- `counterparty` для чека — продавец из чека. Если чек безымянный (частый случай для
  мелких покупок), бэкенд присылает `name` из чека; правило поиска/создания
  контрагента обычное.

[Copilot] источник: telegram; уверенность: 0.93
Классификация: классифицировано как поступление: входящий СФ

### 5.5. Настройки расширения (константы или регистр)

- Организация по умолчанию (если в базе одна — брать её; несколько и константа пуста —
  оставить реквизит пустым и записать предупреждение в журнал: выбор одной из нескольких
  был бы догадкой о деньгах). Реализовано 31.07.2026.
- Склад по умолчанию (используется в том числе шапкой «Авансового отчёта»).
  Фолбэк зеркален организации (согласовано 31.07.2026): константа пуста → если в базе
  ровно один склад без пометки удаления — брать его; несколько → пусто + журнал.
- Разрешить создание контрагентов/номенклатуры (Булево, по умолчанию Истина).
  На физлиц **не распространяется** — они не создаются никогда (§5.3.1).
- Договор с таможней по умолчанию — для поля «Депозит» ГТД, если бэкенд его не прислал.

### 5.6. Успешный ответ

HTTP-коды (согласовано в dev-чате 31.07.2026): **201** — документ создан,
**200** — идемпотентный повтор (`idempotent_hit: true`). Клиент Python принимает любой 2xx.

```json
{
  "draft_id": "c9d4e7f0-...-guid",
  "doc_type_1c": "Поступление товаров и услуг",
  "doc_number": "БП00-000451",
  "status": "draft",
  "idempotent_hit": false
}
```

- `draft_id` — GUID **основного** созданного документа.
- `doc_number` — номер, присвоенный 1С (не входящий).
- `status`: всегда `draft` при создании.

Если операция создала **несколько** документов (сейчас — только
`customs_declaration`, §5.7), добавляется массив `related_docs` с остальными:

```json
{
  "draft_id": "f1c2...-guid-ГТД",
  "doc_type_1c": "ГТД по импорту",
  "doc_number": "БП00-000078",
  "status": "draft",
  "idempotent_hit": false,
  "related_docs": [
    {
      "draft_id": "a9b8...-guid-поступления",
      "doc_type_1c": "Поступление товаров и услуг",
      "doc_number": "БП00-000452",
      "status": "draft"
    }
  ]
}
```

Для операций с одним документом `related_docs` отсутствует или пустой массив.

### 5.7. ГТД по импорту (`customs_declaration`) — приоритет 2

#### 5.7.1. Почему создаются два документа

По методике БП УЗ документ **«ГТД по импорту»** не самостоятелен: он вводится
**на основании «Поступления товаров и услуг»** от иностранного поставщика и при
проведении добавляет таможенные платежи к стоимости уже оприходованного товара.
ГТД без поступления проводится некорректно — распределять пошлину не на что.

Поэтому один вызов с `operation_type: "customs_declaration"` создаёт **пару
документов в одной транзакции**:

1. **Поступление товаров и услуг** — из `counterparty` (иностранный поставщик),
   `items`, `currency`;
2. **ГТД по импорту** на основании первого — из `customs_details`.

Оба — **непроведёнными**. Оба живут под одним ключом идемпотентности: повторный
POST не создаёт ни второго поступления, ни второй ГТД.

#### 5.7.2. Контракт `customs_details`

```json
"customs_details": {
  "declaration_number": "26004/14072026/0001234",
  "declaration_date": "2026-07-14",
  "customs_office": {
    "name": "Ташкентская таможня",
    "tin": "201234567",
    "ref_1c": null
  },
  "deposit_contract": null,
  "vat_deduction": true,
  "vat_deduction_term": "current_document",
  "sections": [
    {
      "customs_value": 520000000,
      "duty_rate": 5.0,
      "duty_sum": 26000000,
      "fee_sum": 500000,
      "vat_sum": 65520000,
      "item_indexes": [0, 1]
    }
  ]
}
```

| Поле | Обяз. | Описание |
|------|-------|----------|
| `declaration_number` | ✅ | Номер ГТД → поле «Номер ГТД» на закладке Главное |
| `declaration_date` | — | Дата декларации; `null` → `doc_date` операции |
| `customs_office` | ✅ | **Таможня** — элемент справочника Контрагенты. Резолвится и создаётся по обычным правилам (§5.1) |
| `deposit_contract` | — | «Депозит» — договор расчётов по таможенным платежам. `null` → взять/создать договор по умолчанию с этим контрагентом (§5.5) |
| `vat_deduction` | — | Флажок «Отразить вычет в книге покупок», по умолчанию `true` |
| `vat_deduction_term` | — | Срок принятия НДС к вычету: `current_document` (по умолчанию), `current_month`, `12_months`, `36_months`. Маппить на соответствующее перечисление конфигурации |
| `sections` | ✅ | Разделы ГТД, ≥1 |

Поля раздела:

| Поле | Обяз. | Описание |
|------|-------|----------|
| `customs_value` | ✅ | Таможенная стоимость товаров раздела, **в сумах** |
| `duty_rate` | — | Ставка пошлины, %. Справочно |
| `duty_sum` | ✅ | Сумма пошлины по разделу. Передаётся **явно**, а не вычисляется из ставки: в ГТД встречается ручная корректировка и специфические ставки |
| `fee_sum` | — | Таможенный сбор по разделу, по умолчанию 0 |
| `vat_sum` | ✅ | НДС, уплаченный на таможне по разделу |
| `item_indexes` | ✅ | Индексы элементов массива `items` (с нуля), входящих в этот раздел |

`item_indexes` — это связь между двумя таблицами закладки «Разделы ГТД»: первая
таблица — сами разделы, вторая — товары внутри выделенного раздела. Каждый индекс
должен встречаться **ровно один раз** по всем разделам; нарушение → 422
`invalid_customs_sections`.

#### 5.7.3. Алгоритм создания

1. **Договор.** Найти у `counterparty` договор вида **«С поставщиком»** с валютой
   `currency`. Не нашли → создать («Основной договор (импорт, {currency})»).
   Валютный договор обязателен — без него поступление импорта проводиться не будет.
2. **Поступление товаров и услуг.** Сначала поискать **непроведённое** поступление
   того же поставщика с тем же «Номером вх. документа» и датой — нашлось →
   переиспользовать его (ГТД привязывается к нему, второе не создаётся; нашлось
   несколько → взять самое позднее и записать предупреждение в журнал).
   Не нашлось → создать: дата = `doc_date`, «Номер вх. документа» =
   `doc_number` (номер инвойса), табличная часть Товары из `items`.
   Реализовано и проверено на стенде 31.07.2026.
   ⚠️ **НДС в поступлении = 0.** При импорте НДС не предъявляется поставщиком —
   он уплачивается на таможне и приходит в `customs_details.sections[].vat_sum`.
   Если бэкенд всё же прислал `items[].vat_rate` ≠ 0 — игнорировать и записать
   ноль (бэкенд валидирует это раньше, но 1С не должна доверять входу).
3. **ГТД по импорту** на основании созданного поступления. Заполнить Таможню,
   Депозит, Номер ГТД, флажок вычета и срок; закладку «Разделы ГТД» —
   разделами из `sections`, товары каждого раздела — строками поступления по
   `item_indexes`.
4. **Распределение.** Пошлину и НДС раздела распределить по товарам раздела
   **пропорционально их стоимости** — программный эквивалент кнопки «Распределить»
   в форме документа. Проверка: сумма распределённого по строкам = `duty_sum`
   (и `vat_sum`) раздела с точностью до 1 сума; расхождение от округления
   отнести на строку с наибольшей стоимостью.
5. Записать оба документа, **при создании не проводить** (проведение пары — §6.1).
   Комментарий §5.4 — в оба.

#### 5.7.4. Что осознанно НЕ делается в v1

- Не заполняется закладка «Авансы»/зачёт депозита — бухгалтер сопоставляет вручную.
- Не создаётся «Поступление доп. расходов» (транспорт, брокер) — отдельная операция v2.
- ~~Не поддерживается ГТД к уже существующему поступлению~~ — **снято 31.07.2026**:
  реализация ищет непроведённое поступление того же поставщика с тем же входящим
  номером и датой и привязывает ГТД к нему (см. §5.7.3 шаг 2). Дубль возможен только
  если существующее поступление **проведено** или заведено с другим номером/датой —
  этот остаточный случай закрывается эндпоинтом поиска документов в v2 (§9).

## 6. Эндпоинт 5: статус + формат ошибок

```
GET /hs/copilot/v1/operations/{draft_id}
```

Найти документ по GUID (искать среди всех видов документов §5.3, включая «ГТД по
импорту»; для документа из пары §5.7 возвращается его собственный статус). Ответ — как §5.6, но
`status`: `draft` (записан, не проведён) | `posted` (проведён) | `rejected`
(помечен на удаление). 404 — если не найден.

### 6.1. Проведение по подтверждению пользователя (добавлено 31.07.2026)

```
POST /hs/copilot/v1/operations/{draft_id}/post
```

Проводит документ, **ранее созданный сервисом** (draft_id обязан быть в регистре
идемпотентности; чужие документы не проводим → 404). Вызывается бэкендом только
после того, как пользователь бота явно нажал кнопку «Провести».

- Пара ГТД (§5.7): draft_id ГТД проводит **оба** документа в порядке
  поступление → ГТД, в одной транзакции; ошибка любого — откат, оба остаются draft.
- Успех → 200, тело как §5.6 со `status: "posted"`.
- Повторный вызов уже проведённого → 200, `status: "posted"` (идемпотентно).
- Ошибка проведения → 422 `posting_failed`, `message` = текст ошибки 1С
  (первая строка, без стектрейса), документ остаётся draft.

**Формат всех ошибок:**

```json
{ "error": { "code": "totals_mismatch", "message": "Итог строк 43500000 ≠ totals.sum 43400000" } }
```

| HTTP | `code` | Когда |
|------|--------|-------|
| 400 | `missing_idempotency_key` | Нет ни заголовка, ни `external_id` |
| 400 | `bad_json` | Тело не парсится / нет обязательных полей |
| 401 | — | Стандартная аутентификация 1С |
| 404 | `not_found` | GET несуществующего draft_id |
| 422 | `unsupported_operation_type` | Неизвестный `operation_type` |
| 422 | `totals_mismatch` | Итоги не сходятся со строками (допуск 1 сум) |
| 422 | `creation_disabled` | Контрагент/номенклатура не найдены, а создание запрещено настройкой |
| 422 | `employee_not_found` | Подотчётное лицо не найдено; физлиц создавать нельзя (§5.3.1) |
| 422 | `missing_details` | Нет `expense_details` для `expense_receipt` или `customs_details` для `customs_declaration` |
| 422 | `invalid_customs_sections` | `item_indexes` выходят за границы `items`, дублируются между разделами или покрывают не все позиции |
| 422 | `posting_failed` | §6.1: 1С не смогла провести документ (текст ошибки — в `message`) |
| 500 | `internal` | Прочее (текст исключения — в журнал регистрации, наружу не отдавать) |

## 7. Безопасность

**Модель прав пересмотрена 14.08.2026 решением владельца проекта.** Прежняя модель
(роль перечисляет права на каждый объект) заменена на «узкую дверь»: у учётной записи
агента нет вообще никаких прав на данные, а доступ к ним живёт внутри методов сервиса.

1. Создать пользователя 1С `CopilotAPI` с ролью **`BA_КопилотAPI`** (в расширении).
   В этой роли **ровно одно право — `Использование` HTTP-сервиса `BA_Copilot`**,
   и ни одного права на справочники, документы, регистры или константы.
2. Все методы HTTP-сервиса **включают привилегированный режим** первой строкой
   (`УстановитьПривилегированныйРежим(Истина)`); фактический доступ к данным даёт
   он, а не роль.
   **Почему так безопаснее прежней модели, а не опаснее:** множество доступных
   агенту операций теперь равно множеству операций, которые сервис реализует, —
   и никак не шире. Утёкшие учётные данные агента не дают ни чтения базы мимо
   методов сервиса, ни выгрузки данных: интерактивно войти этой учётной записью
   нечем, а прав на объекты у неё нет. В прежней модели те же учётные данные
   открывали прямое чтение и запись всех перечисленных справочников и документов.
   **Цена решения, которую нужно знать:** внутри методов сервиса RLS и проверки прав
   не действуют — корректность доступа держится на коде сервиса, поэтому любой новый
   маршрут обязан ограничивать выборку сам (пример: §6.1 проводит только документы,
   созданные этим же сервисом, — проверка по регистру идемпотентности, а не по правам).
3. Роль `BA_ОсновнаяРоль` (полный перечень прав на объекты) сохраняется в расширении
   для интерактивного пользователя-бухгалтера и для отладки. Учётной записи агента
   она **не назначается**.
4. Запретить этому пользователю интерактивный вход (только веб-сервис).
5. Все действия сервиса и так попадают в журнал регистрации под этим пользователем —
   этого достаточно для аудита. Привилегированный режим на запись в журнал не влияет.
6. HTTPS на публикации; учётные данные хранятся на стороне бэкенда в зашифрованном виде.

## 8. Приёмочные тесты (чек-лист)

Эталон поведения — мок-сервер из репозитория (`apps/onec-mock`, FastAPI): при
сомнении в формате ответа поведение должно совпадать с ним.

- [ ] GET counterparties по `tin` — точное совпадение; по `name` — подстрока без учёта регистра.
- [ ] GET items по названию и по 17-значному ИКПУ.
- [ ] POST goods_receipt с `ref_1c` — создан непроведённый «Поступление товаров и услуг», табличная часть и НДС заполнены, комментарий по шаблону §5.4.
- [ ] POST без `ref_1c`, контрагент есть в базе по ИНН — найден, не задублирован.
- [ ] POST с незнакомым контрагентом — контрагент создан (ИНН заполнен), документ создан.
- [ ] Повторный POST с тем же `Idempotency-Key` — тот же `draft_id`, `idempotent_hit: true`, второй документ **не** создан.
- [ ] POST без ключа идемпотентности — 400 `missing_idempotency_key`.
- [ ] POST с `totals.sum`, не равным сумме строк — 422 `totals_mismatch`.
- [ ] Каждый из пяти `operation_type` создаёт свой вид документа.

Приоритетные операции:

- [ ] GET employees по части ФИО — найден, помеченные на удаление исключены.
- [ ] POST `expense_receipt` — создан «Авансовый отчёт», подотчётное лицо = переданное (не константа).
- [ ] POST `expense_receipt` со смешанными `kind` — товары попали на закладку «Товары», услуги на «Прочее».
- [ ] POST `expense_receipt` с неизвестным подотчётным лицом — 422 `employee_not_found`, физлицо **не** создано, документ не создан.
- [ ] POST `customs_declaration` — созданы **два** непроведённых документа, ГТД введена на основании поступления, `related_docs` заполнен.
- [ ] У поступления из пары — валютный договор вида «С поставщиком», НДС в строках = 0.
- [ ] Суммы пошлины и НДС раздела распределены по товарам пропорционально стоимости; сумма распределённого сходится с разделом (±1 сум).
- [ ] Повторный POST `customs_declaration` с тем же ключом — `idempotent_hit: true`, второй пары документов нет.
- [ ] POST `customs_declaration` с `item_indexes`, покрывающими не все позиции — 422 `invalid_customs_sections`, ни один документ не создан.
- [ ] Ошибка на этапе создания ГТД откатывает и уже созданное поступление (одна транзакция).

Проведение (§6.1, добавлено 31.07.2026):

- [ ] POST /operations — документ создан **непроведённым** (создание по-прежнему никогда не проводит).
- [ ] POST /operations/{draft_id}/post — документ проведён, ответ `status: "posted"`.
- [ ] Повторный /post уже проведённого — 200, `posted`, без ошибки.
- [ ] /post для draft_id не из регистра идемпотентности (чужой документ) — 404.
- [ ] /post ГТД из пары — проведены оба (поступление, затем ГТД); ошибка ГТД откатывает проведение поступления.
- [ ] Ошибка проведения (например, пустой склад при контроле остатков) — 422 `posting_failed`, документ остался draft.

Отчёты (§4.7–4.9, добавлено 14.08.2026; эталон поведения — мок `apps/onec-mock`):

- [ ] `/reports/account`: `total` сходится с суммой ПОЛНОГО набора строк, даже при `truncated: true`.
- [ ] `/reports/account?group_by=month`: сумма оборотов по месяцам равна `total` за период.
- [ ] Префиксный счёт (`9420`) включает субсчета.
- [ ] `/reports/sales`: учитываются только проведённые реализации; периоды без продаж возвращаются с нулями.
- [ ] `/reports/sales?dimension=item|counterparty`: суммы breakdown ≤ итога периода; `truncated` выставляется честно.
- [ ] `/reports/cash`: валютный счёт отдаёт `balance` в валюте и `balance_uzs` по курсу на дату.
- [ ] Неизвестный счёт → 404 `account_not_found`; нет обязательных параметров → 400 `bad_request` (формат §6).
- [ ] GET operations/{guid} для записанного → `draft`; после ручного проведения → `posted`.
- [ ] Ни один сценарий не проводит документ автоматически.
- [ ] Под пользователем `CopilotAPI` нельзя открыть конфигуратор/получить лишние данные.
- [ ] Обновление релиза типовой БП 3.0 не ломает расширение (проверка на тестовой базе).
